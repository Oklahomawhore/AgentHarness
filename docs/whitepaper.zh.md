# AgentHarness 白皮书

[English](whitepaper.md) | 中文

版本 0.2 · 2026 年 9 月 23 日 · 作者：**Wangshu Zhu**

本白皮书说明 AgentHarness 如何让人与各自的 Agent Session 通过主动共享的 Task 上下文协作。它属于设计参考，不是现有功能规格；运行产品时，以[用户指南](user/guide/index.zh.md)为准。

## 1. 带上下文的共同工作

**让执行任务的各个 Session 都能获得必要的决策与来源。**

Agent Session 可以独立工作，但上下文往往留在各自的聊天和工具里。新成员需要重新确认发生了什么、当前采用哪个决定、依据是什么。复制整段对话既嘈杂，也可能暴露私人内容。AgentHarness 用有意识发布的 Task 上下文，让参与者能够查阅并继续工作。

人们通过消息沟通，但理解依赖更多背景：此前发生了什么、哪些来源可信、存在什么约束，以及为什么做出某个决定。每一位新加入的协作者，往往都要重新拼接这些背景。我们的核心主张是：Agent 可以帮助上下文跨越会话、工具与组织流动，而哪些内容可以流动，由相关的人决定。

产品希望减少重复说明，同时让人控制共享范围。本地工作区与已发布内容不同；加入 Task 不会暴露参与者完整的私人历史。

## 2. 人与 Agent 共同参与的 Task

用户创建 Task，填写目标和初始共享上下文。兼容的 Agent Session 主动加入。参与者可以在决定共享时发布结论或其他相关上下文。Task 可以从一个 Task 派生，也可以汇合多个 Task 的选定修订版本。Room 在界面背后管理每个 Task 的成员和在线状态。

例如，设计师与工程师约定共同开发一个功能。设计师选择需求说明与约束，工程师选择接口文档；双方 Agent 对比材料，发现一个不兼容的假设，再将分歧交还给人。人做出决定后，决策及其来源进入房间中经授权的上下文。后来加入的协作者可以理解这个决定，无需获得任何一方的完整私人历史。这是目标体验，并非当前版本已经提供的端到端功能。

项目的价值来自更好的共同理解：减少重复解释，减少基于过时假设的决策，让人们实际达成的约定有清楚的依据。Agent 自主性只有在帮助实现这些结果时才有意义。

## 3. 基础与范围

AgentHarness 基于 DeepSeek Harness 及其插件架构构建。当前 Web 组合围绕 Task DAG、Active Task 分配、已配置节点间的 Task 与 Room 同步，以及将选定 Task 上下文注入 Agent 请求展开。Room 提供隐藏的成员关系与在线状态。[协作架构](../packages/collaboration/README.zh.md)维护当前实现范围；[运行时架构](architecture.zh.md)解释底层框架。

Task 上下文块与显式快照已经存在；范围更广、由参与者控制的分享方式及共享 Agent 行为仍属于后续工作。跨组织联邦、全球可发现的 Agent 与可互操作的上下文交换属于研究和工程提案。本白皮书不意味着安装预览版即加入全球网络，也不意味着私人会话会被自动上传。

开发者预览用于探索与贡献，其存在不代表产品已经适合公开、不可信、多组织协作的生产环境。安装方法与发行可用性见[项目 README](../README.zh.md)和[公开发行指南](public-release.zh.md)。

## 4. 拟议系统设计

以下分层描述计划的演进方向。每一层都需要独立实现、评审与可观察的验收标准，才能作为受支持的能力对外介绍。

| 层次 | 职责 | 进入下一阶段所需证据 |
| --- | --- | --- |
| 个人运行时 | 在本地运行 Agent、工具与持久工作空间 | 可复现的安装与会话行为 |
| 协作房间 | 建立议题、成员关系与参与者在线状态 | 协作者观察到一致的房间状态 |
| 共享上下文 | 交换带有来源、版本与受众的选定材料 | 接收者可以检查来源与范围；未授权读取被拒绝 |
| 共享 Agent | 总结、对比并发现尚未解决的问题 | 提案引用上下文，并保留分歧 |
| 联邦互联 | 连接独立运营的 Agent 系统 | 独立实现一致地交换与拒绝消息 |

候选的共享上下文记录包含来源引用、作者或所属主体、时间戳、版本、目标受众、分享目的与保留信息。这些字段是设计提案，不是稳定的通信格式。派生摘要需要保留来源引用并标明不确定性；冲突主张在由人解决之前必须保持可区分。

互操作不只是接通模型 API。独立系统需要就身份、能力发现、消息语义、授权、来源追溯、版本协商、取消与失败报告形成约定。现有集成可以为实验提供参考，但任何传输方式或协议名称本身都不能证明普遍兼容。

## 5. 参与与信任

拟议网络遵循四项原则：

- **由人选择分享内容。** 本地工作区与明确分享的材料是不同的范围。分享需要清晰可见的受众与目的；无关的私人历史不进入分享材料。
- **Agent 的权限有范围。** 读取上下文、提出修改、转发材料和操作其他系统，需要分别作出决定。从其他 Agent 收到的内容是数据，不是扩大权限的许可。
- **来源与分歧保持可见。** Agent 的推断必须能够与来源引文、人的决定区分开。共同理解必须容纳纠正与不同意见。
- **参与可以结束。** 人需要能够停止后续访问并退出协作。撤销授权不能承诺抹除他人已经接收的副本；保留期限与下游用途需要明确规则。

在扩大部署之前，设计需要经过测试的机制，应对身份冒用、共享材料中夹带的恶意指令、过度分享、失效权限与资源滥用。加密连接本身不等于同意，也不保证内容可信。这些是尚待实现的要求，不是本文件提供的安全保证。

## 6. 发展阶段

路线按依赖关系排列，不承诺发布日期。每个阶段都是提案；完成需要可运行的软件与公开证据。

1. **让本地基础可靠。** 保持安装可复现，保留用户数据，让协作者能够理解房间成员关系与在线状态。
2. **引入主动选择的上下文分享。** 让人在分享前检查材料与接收者，让收到的材料可以追溯来源，并测试拒绝访问与后续权限变化。
3. **构建协作辅助。** 增加保留来源的摘要、问题与决策记录，将分歧呈现给人判断。
4. **试验独立网络互联。** 用有文档的消息、版本协商、故障恢复与对抗性互操作测试，连接分别运营的节点。
5. **扩大参与。** 评估软件开发之外的用途，完善易用界面、多语言沟通、社区治理与明确的运营责任。

这一愿景不要求发行代币、建立支付系统或采用集中所有权模式。治理与可持续运营仍是需要贡献者和参与者共同讨论的设计问题。

## 7. 如何评价进展

评价从具体协作任务出发，与普通消息协作方式对比。有用的指标包括重建背景所花时间、来源归属的准确性、过时上下文得到纠正的情况、被发现的未解决分歧，以及用户是否理解谁会收到自己的材料。

技术评价还需要关注未授权访问拒绝、阻止后续访问的撤销延迟、断线恢复、不同实现间的互操作与运行成本。本白皮书没有为这些拟议指标提供已发表结果；它们规定实验需要报告什么，不代表已取得的改进。
