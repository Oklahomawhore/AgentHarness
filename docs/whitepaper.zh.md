# AgentHarness 白皮书

[English](whitepaper.md) | 中文

版本 0.3 · 2026 年 10 月 5 日 · 作者：**Wangshu Zhu**

本白皮书说明 AgentHarness 如何通过持续维护、经过授权的 Task 上下文，连接分属不同人的 Agent。它属于设计参考，不是现有功能规格；运行产品时，以[用户指南](user/guide/index.zh.md)为准。

## 1. 带上下文的共同工作

**让执行任务的各个 Session 都能获得必要的决策与来源。**

人的职责、代码库、凭据、知识和问责关系已经分开。即使一个模型在技术上能完成全部工作，各自的 Agent 也承接了这种分离。AgentHarness 解决这些既有参与者之间的协作，不以证明拆成多个 Agent 能提升模型能力为前提。

人们通过消息沟通，但理解依赖更多背景：此前发生了什么、哪些来源可信、存在什么约束，以及为什么做出某个决定。每一位新加入的协作者，往往都要重新拼接这些背景。我们的核心主张是：人选择协作范围和允许的来源后，Agent 持续维护跨 Session、工具和组织的相关共享事实。目标体验是让每次更新都无需人再次挑选、总结和转发上下文。

产品希望减少重复说明，同时让人控制共享范围。本地工作区与已发布内容不同；加入 Task 不会暴露参与者完整的私人历史。

## 2. 人与 Agent 共同参与的 Task

用户创建 Task，填写目标和初始共享上下文。兼容的 Agent Session 主动加入。参与者授权上下文来源，也可显式发布决定。预期的后台交换提取变化、保留来源，并为相关的既有 Session 准备上下文。Room 是共享上下文范围，不要求 Agent 以群聊对话交换信息。Task 可以从一个 Task 派生，也可以汇合多个 Task 的选定修订版本。Room 在界面背后管理每个 Task 的成员和在线状态。

例如，后端工程师将登录响应字段从 `user_id` 改成 `uid`。前端工程师的 Agent 收到获准更新，调整自己负责的前端类型，运行现有测试并贡献结果。无关的模型部署更新不赋予它获取算法工程师凭据或接管该项工作的权限。超出本人职责的决定交还给负责的人。这是目标体验，其模型行为与权限必须分别验证。

项目的价值来自更好的共同理解：减少重复解释，减少基于过时假设的决策，让人们实际达成的约定有清楚的依据。Agent 自主性只有在帮助实现这些结果时才有意义。

<a id="human-responsibility"></a>
### 协作遵循人的职责

AgentHarness 保留参与者既有的职责，不规定其内部 Agent 架构。共享 Task 成员关系连接他们选择的 Session，不因全局目标可以拆分就创建规划、编码或审查 Agent。参与者可在自己的运行时和权限内使用单 Agent、子 Agent 或工作流。

自动协作的含义是：我的 Agent 可在我本地授权的目标、既有权限和有限额度内响应共享变化。Task 所有者填写的职责可为支持它的 backend 提供依据，不是我的执行同意。传入内容提供证据，不是接管整个 Task 或扩大权限的指令。加入时可以评估一次当前获准快照。后续仅响应相关新证据是目标；相关性取决于所选 backend，默认 Text 不按职责做语义筛选，无关的新发布仍可能触发工作。

职责描述不是文件系统 ACL，也不能证明模型一定遵从。当前读取可能授权整个 Root Task，贡献目录限定的是向外分享范围，而非工具执行范围。运行时工具权限和审批仍独立存在。产品评价必须报告这些区别，不能把角色提示当成已强制执行的隔离。

## 3. 基础与范围

AgentHarness 基于 DeepSeek Harness 及其插件架构构建。当前 Web 组合围绕 Task DAG、Active Task 分配、已配置节点间的 Task 与 Room 同步，以及将选定 Task 上下文注入 Agent 请求展开。Room 提供隐藏的成员关系与在线状态。[协作架构](../packages/collaboration/README.zh.md)维护当前实现范围；[运行时架构](architecture.zh.md)解释底层框架。

源码已包含[独立读取授权和原生文件贡献](user/guide/collaboration-network.zh.md)、[面向接收者的上下文 backend](user/guide/collaboration-semantic.zh.md)和[显式有限原生自动工作](../packages/collaboration/scope-agent-context/README.zh.md)。这些机制不证明完整目标体验或真实模型协作收益已经成立。跨组织联邦、全球可发现的 Agent 与可互操作的上下文交换属于研究和工程提案。本白皮书不意味着安装预览版即加入全球网络，也不意味着私人会话会被自动上传。

开发者预览用于探索与贡献，其存在不代表产品已经适合公开、不可信、多组织协作的生产环境。安装方法与发行可用性见[项目 README](../README.zh.md)和[公开发行指南](public-release.zh.md)。

## 4. 拟议系统设计

以下分层描述计划的演进方向。每一层都需要独立实现、评审与可观察的验收标准，才能作为受支持的能力对外介绍。

| 层次 | 职责 | 进入下一阶段所需证据 |
| --- | --- | --- |
| 个人运行时 | 在本地运行 Agent、工具与持久工作空间 | 可复现的安装与会话行为 |
| 协作房间 | 建立议题、成员关系与参与者在线状态 | 协作者观察到一致的房间状态 |
| 共享上下文 | 交换带有来源、版本与受众的选定材料 | 接收者可以检查来源与范围；未授权读取被拒绝 |
| 上下文 backend | 为既有接收 Session 选择和总结证据 | 当前证据、来源、纠正与未解决分歧在投递后仍被保留 |
| 联邦互联 | 连接独立运营的 Agent 系统 | 独立实现一致地交换与拒绝消息 |

通信编码可独立于参与关系和执行许可替换。自然语言摘要和拟议向量表示均需要明确的接收端支持与保真验证；不同编码本身不授权新动作，也不证明互操作。

候选的共享上下文记录包含来源引用、作者或所属主体、时间戳、版本、目标受众、分享目的与保留信息。这些字段是设计提案，不是稳定的通信格式。派生摘要需要保留来源引用并标明不确定性；冲突主张在由人解决之前必须保持可区分。

互操作不只是接通模型 API。独立系统需要就身份、能力发现、消息语义、授权、来源追溯、版本协商、取消与失败报告形成约定。现有集成可以为实验提供参考，但任何传输方式或协议名称本身都不能证明普遍兼容。

## 5. 参与与信任

拟议网络遵循四项原则：

- **由人选择范围和来源。** 本地工作区与获准贡献是不同的范围。人选择受众、目的和允许的来源后，后台交换可持续更新，无需逐条挑选消息。无关的私人历史不进入分享材料。
- **Agent 的权限有范围。** 读取上下文、提出修改、转发材料和操作其他系统，需要分别作出决定。从其他 Agent 收到的内容是数据，不是扩大权限的许可。
- **来源与分歧保持可见。** Agent 的推断必须能够与来源引文、人的决定区分开。共同理解必须容纳纠正与不同意见。
- **参与可以结束。** 人需要能够停止后续访问并退出协作。撤销授权不能承诺抹除他人已经接收的副本；保留期限与下游用途需要明确规则。

在扩大部署之前，设计需要经过测试的机制，应对身份冒用、共享材料中夹带的恶意指令、过度分享、失效权限与资源滥用。加密连接本身不等于同意，也不保证内容可信。这些是尚待实现的要求，不是本文件提供的安全保证。

## 6. 发展阶段

路线按依赖关系排列，不承诺发布日期。每个阶段都是提案；完成需要可运行的软件与公开证据。

1. **让本地基础可靠。** 保持安装可复现，保留用户数据，让协作者能够理解房间成员关系与在线状态。
2. **自动维护获准上下文。** 让参与者选择来源和接收者后，持续传播更新、纠正和撤回，并保留来源。测试拒绝访问与权限变化。
3. **构建协作辅助。** 增加保留来源的摘要、问题与决策记录，将分歧呈现给人判断。
4. **试验独立网络互联。** 用有文档的消息、版本协商、故障恢复与对抗性互操作测试，连接分别运营的节点。
5. **扩大参与。** 评估软件开发之外的用途，完善易用界面、多语言沟通、社区治理与明确的运营责任。

这一愿景不要求发行代币、建立支付系统或采用集中所有权模式。治理与可持续运营仍是需要贡献者和参与者共同讨论的设计问题。

## 7. 如何评价进展

评价从人的所有权、职责、凭据和工作区已经分开的具体任务出发。比较人工协调、显式记忆检索与自动上下文投递时，保持这些分配不变。测量同步负担、纠正延迟、当前事实采用、任务质量、无效唤醒和总成本。重复投递与无关变化需要反例；一个人运行时内部的委派不能作为跨人协作证据。

单 Agent 对比在获准访问条件相同时有意义。把所有参与者的凭据交给一个 Agent 改变了前提，必须作为另一种场景报告；产品无需宣称多个 Agent 天然更优。

技术评价还需要关注未授权访问拒绝、阻止后续访问的撤销延迟、断线恢复、不同实现间的互操作与运行成本。本白皮书没有为这些拟议指标提供已发表结果；它们规定实验需要报告什么，不代表已取得的改进。
