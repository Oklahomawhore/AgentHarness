# Long scope history snapshot

English | [中文](README.zh.md)

This reference describes the keyless `sdk/scope-history-capacity` scenario. The shipped SDK profile owns the receiving Session. Two private Loader Hosts own the Task and a source Session with production filesystem tools. Their authenticated transport runs in one process; this scenario does not establish a cross-device connection.

The fixture submits 500 synthetic, authorized complete-file Write reports through ScopeAccess. Each report has a distinct hash identifier and supersedes the same file. The source Agent then performs two real Write tools, each followed by a controlled completion. After verifying each tool result, resulting file, and flushed Session log, the fixture submits its report through the same contribution API. These submissions are fixture-driven; the scenario does not test automatic collection or claim 500 actual tool executions.

Two ordinary recipient requests carry the latest report and its correction without recall tools or factual user prompts. Each decoded projection retains every earlier publication reference, in order, as an explicit superseded omission. The current request excludes earlier file bodies. The fixture measures the actual complete encoded read response below 60,000 bytes and the equivalent uncompressed response above that limit; decoding remains limited to 2 MiB. Managed request context stays within 8,000 bytes. The transport observation covers the response JSON, not a physical network frame.

Both recipient requests are compared with full detached reconstruction from memory and flushed disk events before normalization. The earlier admitted context remains in durable history after correction. The source makes four controlled model requests and two real filesystem writes; the recipient makes two recorded requests. No paid model is called and no model-quality claim follows from the replay. [Testing](../../../docs/testing.md) owns the shipped-profile snapshot runners and built-artifact requirements.
