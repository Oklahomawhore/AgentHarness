# Agent Note: 协作 scope 的接收者专属上下文后端

Status: proposed

[English](2026-10-02-scope-context-backends.md) | 中文

## 问题

不同拥有者的 Agent Session（会话）已有各自职责、权限和工作上下文。要求人维护发布内容或逐一唤醒空闲接收者，会把协调工作留给用户。[Task 绑定模型](../../implemented/architecture/2026-08-28-task-context-atoms-and-session-bindings.zh.md)提供 scope 身份；自动来源采集、接收者选择和投递需要各自的授权与生命周期。

共享对话记录或整个房间的一份滚动摘要无法区分前端会话的依赖与评审会话的职责。反复分发所有变化还会消耗上下文、使请求前缀缓存失效，并可能让一个会话继续另一个会话未完成的工作。[Mastra 的观察记忆 scope 指引](https://mastra.ai/docs/memory/observational-memory#scopes)记录了相关系统中的这种失败情况。

## 提案

本地外部会话部分由 [Claude 适配器决策](../../implemented/architecture/2026-10-02-claude-scope-adapter.zh.md) 拥有；支持的文件声明子集由 [API 采样决策](../../implemented/architecture/2026-10-03-sampled-api-context.zh.md) 拥有。[独立读取](../../implemented/architecture/2026-10-03-independent-scope-read-grants.zh.md)、[独立贡献](../../implemented/architecture/2026-10-03-independent-scope-contributions.zh.md)和[原生 Session 控制](../../implemented/architecture/2026-10-03-native-scope-session-controls.zh.md)分别拥有已实现的授权与投递机制。[接收方证据决策](../../implemented/architecture/2026-10-03-recipient-evidence-activation.zh.md)拥有受支持声明的自动启动比较。通用工作采集、跨机器加入、外部空闲投递与可测量的协作收益仍是产品验收义务。

协作 scope 定义共同目标与参与会话的绑定。其内部事件不要求以对话界面呈现。产品自动把相关工作变化转成各参与会话所需的上下文；用户可以在排查行为时检查来源和投递状态，而无需维护信息交换。

后端计算接收者专属上下文。源适配器采集工作，transport 认证 scope 内的交换，会话适配器投递上下文。这些职责保持分离，使替换投影 provider 不会暗中改变成员关系、来源访问或唤醒行为。以下工程增量与自动协作阶段各有独立的验收标准。

### 首个增量：可替换的文本投影

在现有 [development-task-context 包](../../../../packages/collaboration/development-task-context/README.zh.md)内，以 `/backend` 入口承载 Service Definition，以 `/text` 承载文本 Service Provider。当前 pre-step Consumer 注入后端服务。这些角色尚不需要拆成独立包；首个增量不新增外部会话 Consumer、自动采集或唤醒调度器。

首个 provider 对现有 Task 发布内容及继承来源进行确定性筛选。请求包含来源快照、接收者绑定、取消信号和完整输出的字节预算。结果标识已包含来源，并明确报告被排除或因预算而省略的材料。筛选可以排除接收者自己的发布，但这不能证明内容与其职责在语义上相关。provider 保留选中文本和来源归属，不声称能够摘要、验证或协调事实。

Consumer 在 Session 中记录实际选中的输出，并按配置上限检查完整渲染消息。重放使用已记录输出，不再次筛选。不能仅因检查过某个来源修订，就把投影中省略的材料报告为已采用。替换 provider 会产生新投影，不重新解释已提交输出。

这个增量建立可用后端，保留现有的显式来源与请求时投递行为。它是工程前提，尚未满足日常工作自动到达另一位 agent 的产品要求。面向职责的相关性、自动采集、空闲投递和外部客户端集成需要以下阶段。

### 自动协作阶段

以下义务适用于来源采集和投递独立于接收请求运行的情况。它们必须与所属适配器及持久化支持一并落地，不能作为未受支持的字段预先加入首个文本后端。

### 输入与输出义务

| 对象 | 必需行为 |
|---|---|
| 来源输入 | 不可变记录标识产生它的节点、会话、绑定有效区间和耐久事件。顺序限定在单个来源内；水位映射追踪多个产生者，不暗示存在全局顺序。由 owner 串行化的事件流必须说明对该 owner 的依赖。 |
| 接收者输入 | 绑定 epoch（有效区间标识）、共同目标、接收者职责、来源水位、上次采用的投影、支持的表示及配置预算共同决定投影请求。 |
| 计算 | 后端可以在内部总结、筛选、协调或使用 embedding 检索。它不得要求所有接收者共用一份摘要，也不依赖模型决定调用 recall。 |
| 输出 | 投影记录后端修订、准确来源引用、来源水位、覆盖范围及投递表示。结论失效需要明确的来源身份与撤回操作；未决冲突保留双方来源。 |
| 提交 | Consumer 拒绝绑定 epoch 已变化或来源依据已被明确废止的结果。新追加的输入可以排队触发新计算，不必使仍可使用的结果失效。采用操作绝不把接收者退回更旧的来源依据。 |
| 重放 | 接收者 Session 中提交的输出和水位是采用状态的权威。确认消息是幂等的派生回执。恢复从该日志重建已采用状态，不调用后端重建历史输入。 |
| 投递 | 会话适配器声明支持的投递时点。运行时接收、进入请求和观察到的下游行为分别度量。 |
| 反馈 | 采集只准入已声明的来源事件类型，并记录其触发输入与派生状态。直接注入的投影及已标记的派生输出不成为独立证据。新的事件身份本身不能证明出现了新观察。 |

绑定区间使用耐久 `task-bound` 事件的 `(nodeId, seq)` 身份作为 epoch，不使用可复用的绑定 id 或时间戳。采集、待处理计算和最终采用均保留该 epoch，因此离开 scope A 后再回到 A，不会准入上一次停留期间的结果。provider 声称可以使事实失效之前，必须先实现来源撤回协议；当前 Task 发布模型本身没有提供这种协议。

基于模型的 provider 必须在公共评估案例中保留关键标识、数值、否定和未决矛盾。这是需要度量的质量要求，不保证摘要器能识别所有错误陈述。明确冲突的证据继续保留，不按到达先后决定哪方正确。

### 采集与执行

每个采集适配器声明可执行的已提交工作事件白名单及其触发输入。仅用用户可见工作这一概述，不足以准入所有 assistant 消息或工具结果。适配器只准入其记录的绑定 epoch 期间的事件；区间之外的私有会话、隐藏推理和任意本地文件不自动成为来源。加入时一次确立采集策略，日常更新无需发布审批。外部来源无法采集时明确报告为不支持。

每个接收者的 Host 拥有自己的投影与投递状态。scope 的来源记录独立于接收者摘要。自动采集初期可以复用 Task owner 路由和 Mesh 复制，但必须说明该依赖；独立执行不能证明无主节点写入或网络分区时仍可用。跨来源时间戳不能确定冲突结论中哪一方正确。

已提交的来源变化合并为有界的待处理接收者工作。较新的追加事件等待处理时，Consumer 可以先采用仍获授权的结果，再投影这些新事件；持续输入不能导致所有结果无限期被丢弃。晚完成的计算不能覆盖较新且已采用的投影。绑定改变、来源撤回和访问撤销属于失效操作，不是普通追加。

原生 Consumer 使用现有 inbox 和生命周期操作：单独注入上下文不会唤醒空闲 agent，受支持的 steering（中途引导）可以启动或影响工作。投递作用于 Host 收到变化后，适配器可控制的下一次请求或操作时点。它不能修改已发出的模型请求，也不保证中断任意运行中的工具。外部适配器证明各自的空闲和忙碌路径；MCP 通知本身不能证明模型收到内容。

断开与重新绑定使待处理计算失效，并从下次获准请求中移除先前 scope 的投影。历史日志保持完整。被拒绝、取消或失败的投影绝不推进采用状态。如果接收者在提交输出后、发出确认前崩溃，恢复时只重试回执，不再次采用同一输出。运行时限制覆盖完整输出、待处理工作、重试和处理时间。

没有符合准入条件的来源变化时，自动交换回到空闲。因果身份可抑制直接重复，但不能证明未标记的 assistant 改写属于独立证据，也不能证明任意模型交互会终止。采集规则区分派生输出与新的外部观察，有界处理防止工作失控。评估包含改写和矛盾观察；prompt 要求或语义相似度本身都不能证明反馈终止。

### 首个外部适配器实验

首个 Claude Code 实验使用明确加入同一本地拥有 Task 的两个主会话。command hook 通过自定义 `dsh` profile 运行，并使用 Host 现有认证连接。临时 profile 和真实 Connection fixture 先验证启动、令牌交换、RPC、输出刷新和关闭路径。这个受控部署不能证明独立拥有者或跨节点集成。

适配器在工作开始前的 PreToolUse 阶段记录耐久租约。完成事件必须匹配租约的会话、工具身份、输入摘要、绑定 epoch 和当前采集策略修订。租约缺失、重新绑定或其他 hook 改写输入都会拒绝采集，不改变工具自身的许可决定。观察身份在重试和重启后保持不变；Task owner 将去重与发布一起串行执行。

初始白名单涵盖明确获准的 Edit、Write 和受限制的 Bash 观察。prompt 正文、assistant 自由文本、Read 结果、MCP 结果和子 agent 事件不自动成为来源。UserPromptSubmit 与 PostToolBatch 请求上下文，不发布自身载荷。耐久的外部投影记录保存准确文本与覆盖范围；适配器不伪造原生 Session 来声称采用。

Claude hook 的 stdout 只确认本地输出：其他 hook 或请求取消仍可能阻止内容进入模型。没有宿主采用回执时，每次受支持的注入事件都重送当前准确投影；缓存节省计算，不省略投递。外部 additionalContext 会追加到历史，因此新投影标明其前序投影，撤回内容将其标为失效，而不声称擦除先前上下文。下一请求投递工作后，空闲唤醒还需要单独验证路径。官方集成细节以 [Claude Hooks](https://code.claude.com/docs/en/hooks) 为准。

### 表示形式

embedding 检索可以立即用于相关性与去重，投递仍可保持文本。隐藏状态或 KV Cache 传输属于不同 provider 类别，需要兼容的模型内部能力及明确的接收端支持。[LatentMAS](https://arxiv.org/html/2511.20639v3)假设兼容的 Transformer 结构，[Interlat](https://arxiv.org/html/2511.09149)训练通信组件并说明了仅提供 API 的模型限制。将向量序列化为文本不构成潜在表示通信。

真实接收者存在前，不发布未使用的 latent 载荷变体。新增一种编码时，一并提供 provider、接收适配器、持久化表示和兼容性测试。不支持的编码明确失败；任何配置的文本转换记录为转换，不描述为 latent 投递。

## 考虑过的替代方案

**保留显式发布作为常规路径。** 它能提供明确选定的证据，但保留了产品希望消除的人工协调工作。显式来源提交可以保留为可选输入，而不是所有交换的前提。

**向所有成员发送一份共享摘要。** 它是有用的评估对照，但混合职责，并让无关变化影响每个请求。接收者专属投影保留共同 scope，同时把各会话限制在相关状态内。

**建立隐藏的 agent 聊天，再事后总结。** 隐藏对话不会减少冗余协商，也不保证相关事实在依赖动作之前到达。交换必须由来源变化与接收者需要驱动，而不是由回复义务驱动。

**让后端同时承担传输与语义处理。** 这会在每个 provider 中重复唤醒、重试、成员关系和重放规则。后端计算上下文，运行时和适配器负责投递。

**从通用 embedding 或 KV 通信开始。** 现有闭源客户端集成提供文本，而不是可互换的模型内部表示。文本和结构化上下文可以先证明产品价值；兼容接收者存在后，再独立评估 latent 表示。

## 验收标准

### 工程前提

1. 文本 Provider 继承 `/backend` 导出的 Service Definition；真实 Loader 组合从同一个包挂载 `/text` 和当前 Consumer。替换 provider 会改变实际请求上下文，不只是调用未被使用的注册表。
2. 确定性来源筛选保留选中文本及归属，报告覆盖范围，并限制包括 Unicode 和元数据在内的完整渲染输出。省略的材料不确认为已采用。
3. 记录会话场景保留实际注入结果；重放和重启不重新计算历史输出。断开会从下次获准请求中移除先前上下文，不删除历史。
4. 来源筛选测试区分接收者身份、已包含来源、被排除的自身材料以及预算省略项。它们不能替代语义相关性、自动采集、空闲投递或外部客户端测试。

### 自动协作产品标准

1. 独立拥有者把已有会话接入共同 scope，无需由同一主管创建所有参与者。日常工作自动到达另一位 agent，不要求手工发布、复制上下文或提醒查询 inbox。
2. 前端会话与评审者从同一输入轨迹收到不同的相关投影。非成员两者都不收到；关键值和未决矛盾经过处理后仍保留。真实模型评估观察依赖编辑或测试，不只检查口头确认。
3. 最初只有一位参与者知道的未预告变化到达另一台 Host，并在下一个受支持的请求或操作时点改变其依赖工作。分别度量来源到 Host、Host 到请求、请求到行动的延迟，包括旧工作可能继续的时间区间。
4. 延迟计算在持续追加输入时不会饥饿，不能回退采用状态，并会在 A 到 B 再到 A 的绑定切换后被拒绝。来源撤回和访问撤销测试与对应操作一并落地。
5. Session 提交后、确认前崩溃的恢复不重复采用。忙碌、空闲、离线重入、取消、重复投递、重启和 provider dispose（资源释放）遵守同一套已记录的采用规则。
6. 采集测试拒绝把直接注入的投影和已标记的派生输出当作独立证据，同时准入符合条件的新工具观察。重复和改写更新验证配置的处理上限；没有符合条件的变化时，自动交换回到空闲。
7. 同一来源轨迹比较原始事件投递、共享滚动摘要、接收者投影以及缺失或错配的更新。一并报告正确性、人工协调、额外模型费用、无关上下文和延迟。多节点案例经 Mesh 到达接收者的耐久 Session。
8. 声称支持已有 agent 集成前，至少一个受支持的外部客户端证明其采集与投递路径。代表性用户试用验证安装、加入、恢复工作、诊断错误更新及离开。仅凭原生测试与后端增量不能判定产品成熟。

## 风险

如果没有在事件准入操作中执行绑定区间与来源策略，自动采集可能分享无关工作。语义压缩可能遗漏否定、混合不相容结论，或保留已撤回事实。细粒度投影可能增加计算与缓存失效，超过节省的成本。声称效率提升前，使用公共来源轨迹度量这些问题。

接收者无法在任意 Host 操作期间行动；投递承诺始终对应已证明的适配器能力。Task owner 路由在单独重设计前也仍是故障依赖。产品可以减少日常上下文同步，但无法消除人类拥有者之间真实的分歧，也无法恢复任何参与者都未观察到的事实。

各增量落地前，现有 Task 决策仍是已发布行为的依据。本提案部分替代其显式发布策略，保留独立绑定与历史来源。仅凭这份提案，没有任何活跃决策记录被完全替代或符合归档条件。
