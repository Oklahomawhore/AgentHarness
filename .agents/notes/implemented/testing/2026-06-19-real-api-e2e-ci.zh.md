# Agent Note: 在 CI 中对外部 DeepSeek API 运行真实 API e2e 测试

Status: implemented

[English](2026-06-19-real-api-e2e-ci.md) | 中文

## 问题

无密钥回放证明确定性的管线，但不能证明发布的 agent 能与线上提供方正常工作。[ACP inject 事故复盘](../../../../docs/postmortem/0001-acp-default-export-drops-inject.zh.md)记录了 178 项无密钥测试通过时真实客户端仍然失败的情况。另一方面，不带凭据的真实 API 套件可能自动跳过，无法提供任何提供方证据。

## 决策

[托管 CI 决策](../process/2026-10-25-agentharness-hosted-ci.zh.md)取代本文的自动 PR、push 和每夜触发策略。自动验证不使用密钥。独立的[真实 API 工作流](../../../../.github/workflows/e2e.yml)仅接受显式 `workflow_dispatch`，并保留下述提供方专用预检和凭据控制。本文继续拥有实际提供方执行及其凭据策略为何独立于回放的依据。

### 提供方证据与预检

手动工作流针对外部 DeepSeek API 运行 `pnpm run test:e2e`。缺少 `DEEPSEEK_API_KEY_EXTERNAL` 时，预检在可自动跳过的套件报出虚假通过前失败。预检指出缺失的 secret 名称，不打印其值或长度。无密钥运行成功不能替代实际提供方运行；[测试策略](../../../../docs/testing.zh.md)拥有这一区分。

工作流先构建运行时，再由 profile 子进程在普通 Node 下消费包导出。其 Node 24 测试进程使用 workspace 源码解析器、有界且可配置的 worker 池、逐测试重试和 job 超时。无密钥验证及 Node 兼容性仍归主工作流。显式 dispatch 不会使提供方失败或缺失凭据成为可选的成功。

### 凭据范围

仓库 secret `DEEPSEEK_API_KEY_EXTERNAL` 仅在预检和测试步骤的环境中映射为适配器使用的 `DEEPSEEK_API_KEY`。checkout、工具设置、安装和构建不接收这个环境值。这限制了这些步骤中的环境暴露，但不能使选定的携密钥测试步骤代码自动可信。

job 使用 `contents: read`。测试步骤将 `DEEPSEEK_BASE_URL` 固定为 `https://api.deepseek.com`，防止仓库 `.env` 重定向此次运行。工作流及其预检均不回显凭据。手动 dispatch 决定何时消耗模型账户资源，但仍需评审选定代码及其 secret 访问权限。

### 触发器与仓库风险

上游自动 PR 策略曾为合并前反馈接受更大的暴露面：有写权限作者分支上的代码会接收密钥。其基于作者的 Dependabot 和 fork 跳过只是便利措施，并非安全机制；GitHub 的 secret 扣留才提供保护。当前手动工作流没有这些触发器或跳过条件。重新考虑自动提供方运行时，这项历史权衡仍有参考价值。

fork PR 的普通 `pull_request` 运行不接收仓库 secret；批准这类运行本身不会授予 secret。若将触发器改为 `pull_request_target`，同时检出并执行不可信代码，就可能暴露基础仓库的 secret。这不是为 fork 获得提供方覆盖的安全方式。仓库可见性也影响谁能阅读日志；即使运行由显式请求触发，输出仍不能包含 secret。工作流触发器和步骤范围不能替代仓库访问控制、评审或疑似暴露后的凭据轮换。

### 覆盖限制

早期原生 DeepSeek `web_search` 探测曾因兼容端点成功返回却没有结构化来源块而保持跳过。当前 e2e 清单没有该探测；此工作流不声称已验证线上来源块的 wire format。

## 曾考虑的替代方案

**在自动 CI 中加入消费 secret 的 job。** 已否决，因为回放与提供方账户执行的触发和凭据要求不同。凭据是否可用不能决定 fork 是否获得完整的无密钥验证结果。

**自动运行可信 PR 的提供方测试。** 上游决策为更早反馈接受了合并前 secret 暴露。托管 CI 决策以显式 dispatch 取代这一选择；保留安全分析可防止在未考虑哪些代码会接收凭据的情况下重新引入它。

**配置的 secret 缺失时允许套件跳过。** 已否决，因为手动的提供方验证请求会在未调用提供方时表现为成功。预检使这项配置错误可见。

## 后果

真实 API 验证仅在显式请求时消耗账户资源。其证据独立于录制回放，但不是自动 PR、合并后或每夜信号。独立工作流和限域凭据仍需要维护。提供方行为、运行器出站连接、凭据可用性以及选定版本仍需实际成功运行验证；仅有工作流配置不能证明这些事实。
