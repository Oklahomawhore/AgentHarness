# Emergence Center UI

English | [中文](README.zh.md)

## Summary

`@deepseek-ai/dsh-client-ui-emergence-center` presents a searchable shared-context workspace over immutable Root, Fork, and Merge Task lineage. The left column owns identity, search, and Task selection; the center renders the read-only DAG; the right column puts Agent-session connection first and explicit shared context second. Task workflow has no lifecycle, evidence, completion, or audit controls; observation grants have separate owner controls.

## Behavior

Independent-device controls expose the local public identity, a recipient-pinned Root Task read invitation, and revocation. A recipient pastes the invitation and selects one observed Claude session without creating a local Task or authorizing directory reads. New receiving requires a ready session catalog; stopping an existing receive remains available while that catalog is unavailable. The panel reports the latest prepared context or unavailable, expired, and revoked state; it does not report model understanding. Direct network addresses must be reachable, and the default loopback listener supports only this computer.

Invitation and approval controls offer only addresses currently published by the Host identity. Several addresses require an explicit choice; a removed address cannot remain selected. Loopback choices are marked as local to the device running AgentHarness. To change the listener, use [Settings → Plugins → Collaboration network](../../bundle/web-app/README.md#scope-collaboration-network) on that device’s local page, save, and manually restart the Host before refreshing these addresses. Saving does not make the selected network reachable or change any Task permission.

The current native Session's header has a Collaboration entry. Its shared-goal paste field accepts a read invitation, a single-session joint entry, a reusable group entry, or a tool-observation contribution entry. A read invitation leads to explicit connection, with passive receipt selected by default. An application entry opens the existing sharing panel, where the user verifies the connection before completing its permission form; pasting or recognizing it grants no permission. Automatic collaboration requires an explicit local goal, additional start allowance, per-turn step limit, and minimum interval; the invited responsibility never fills or authorizes that goal. The form adds the requested allowance to the latest confirmed lifetime reservation count. Cancelled reservations still count, and this allowance does not cap tokens, cost, or provider retries. Cold, delegated, and forked Agents cannot accept a remote read invitation; it never creates an Agent or sends a prompt to establish eligibility.

After connection, Task and device identifiers and the entry paste field remain available in expandable sections. Responsibility, local permission, and pause/leave controls remain visible. The entry displays local mode, pause reason, reservation usage, and recorded activity for the current automatic goal. Its activity card distinguishes reservations, actual requests, completed turns, unchanged-evidence skips, and pauses for incomplete evidence without exposing shared bodies. Pause cancels this feature's current automatic turn and prevents new automatic starts while preserving manual work and remaining reservations. Resume can reuse the same permission's remaining allowance without increasing its ceiling. Leave ends local receiving without erasing history or requests already sent. Expired, revoked, missing, or left subscriptions cannot be resumed directly. View sources selects the existing Trajectory view. A local active subscription is receiving intent, not proof of current owner authorization or model adoption; [native scope context](../../collaboration/scope-agent-context/README.md) owns request-time validation and execution semantics.

For a goal created on this device, select an owned Root Task by name and explicitly connect the current live Session. Connection requires a ready Task catalog, including submission of a retained form. Connection enables context in later requests; it neither shares file work nor starts idle turns. A separate empty permission form authorizes selected directories, write/edit operations, expiry, and sample limits. Its submission carries the observed Task binding and epoch; a changed binding requires renewed consent. Stop sharing withdraws this local source while retaining the reading connection. A separate, initially disabled automatic-work form authorizes a finite goal and allowance for the exact Task binding epoch. Pause retains that policy; turning automatic work off clears it while retaining reads, file permission, and cumulative usage. Leave local goal uses one guarded Host command to stop automatic work, end local captures, and clear the observed Task assignment; an uncertain result requires rereading status. Changing assignment or execution binding clears unsubmitted automatic consent. A disconnected local automatic permission can be cleared or explicitly replaced by a remote invitation without reusing its automatic permission. Task creation remains in the collaboration center.

The native Collaboration entry also offers separate file-work sharing. A Session can retain its local Task, automatic goal, and local capture while applying to contribute file work to another owner. Each destination has its own displayed permission, pending operation, and stop action; the local action uses `stopLocal`, and peer contribution uses `stop`. Selecting a destination stays under the user's control when either capture changes. This contribution permission does not add remote reading or change the existing automatic goal. Paste a tool-observation application entry and check its connection. After parsing the entry, a read-only online check must confirm that it is available before the permission form appears; checking does not create an application or grant. Unavailable, claimed, closed, expired, denied, and capacity-limited entries keep the form hidden. Then select local directories and write/edit operations, set finite expiry and sample limits, and explicitly permit activation after owner approval. An eligible local capture prefills directories, tools, and limits once without replacing edits; sharing and automatic consent start off. Editing the entry, changing Session, or establishing an application clears the check result; late replies cannot reopen an old form. A successful check confirms neither approval nor synchronization. The form shows collection, application, pending-submission, and withdrawal states without displaying captured content or claiming model adoption. Stop carries the displayed capture identity and remains available for an ineligible or inactive Agent; failed confirmation disables further mutations until status is reread. Sent operations remain locked across reconnection. Receiving and automatic-start permissions do not authorize sharing. [Native source contribution](../../collaboration/scope-agent-contribution/README.md) owns capture and durable recovery.

Native file-permission forms offer **Use current workspace suggestions** when no existing local capture supplies the draft. The Host supplies the selected Session’s directory, visible Write/Edit tools and configured limits. Suggestions remain editable and require separate consent. Late responses after entry, Session, assignment, capture or draft edits are discarded; ordinary status refreshes preserve the draft. Applying suggestions clears all form consents, while editing file scope or limits clears collection and complete-content consent. [Permission drafts](../../../.agents/notes/implemented/feature/2026-10-07-native-permission-drafts.md) owns this decision.

Both native file-work forms separately offer “Share complete file contents after changes”, initially unchecked. It authorizes the completion text produced by successful permitted native file operations, including unchanged parts, within the displayed directories, tools, expiry, and sample limits. It performs no additional file read or scan and does not establish disk contents at delivery time. Changing Session, application entry, capture identity, or permission fields clears unsubmitted full-content consent; ordinary status refresh retains it. This permission cannot be combined with recorded-tool initialization and does not upgrade existing captures or historical observations. Owner permission summaries and source status identify the selected content scope. Claude collection does not offer this permission.

Native forms also offer “Share results from selected commands”, initially unchecked. Each exact command selects one entered directory as its working directory; subdirectories are not included. Commands may accompany file tools or be shared alone, using the same limits. Suggestions do not guess commands or grant sharing. Editing a command, directory or limit requires renewed collection consent; entry and Session changes clear the selection. Owner summaries show command text and directory numbers, without local directory paths. This permission shares future foreground results, including failures, but does not execute commands or change tool permissions. It cannot include recorded-tool initialization. Stopping a mixed capture withdraws both its file and command reports while retaining adopted reading and the separate local capture. Existing permissions require a new application; a retained joint read must be left before rejoining with commands. Claude does not offer this native permission.

The same file-work form offers a separate, initially unchecked option to share completed tool observations already saved by the current local capture. It reuses the displayed directories, tools, and combined historical/live allowance. Consent fixes the capture, Task epoch, entry, and permission fields; ordinary new sample updates retain consent, while changed identity or scope clears it. Owner proposals and approved permissions identify historical sharing. The source shows pending selection, frozen selected/excluded counts, observations still incomplete at cutoff, and actual owner acknowledgements separately. These counts do not establish current file contents, complete historical coverage, or model adoption. No file scan is performed.

A native Session without another remote receive binding can use “Invite one session to join” to request reading and file contribution together, with an optional finite automatic-work permission chosen locally. The owner creates one single-capture entry; the source separately confirms whole-Root-Task reading and selected directories, tools, and limits, then the owner explicitly approves both with a responsibility. An existing local Task, assignment epoch, and file capture remain in place. Read consent fixes that exact local target, the execution binding, and its reading-management sequence; changed local responsibility requires renewed consent. Responsibility guides context routing and is not a read ACL. The same form offers an initially unchecked automatic-work option with an explicit goal, additional start allowance, step limit, and minimum interval. Selecting it can prefill the original local goal, but never transfers the old automatic permission to the shared scope. Approval connects receiving and any saved automatic permission in the original Session without another form, invitation transfer, or user prompt. Omission keeps passive receiving. Owner approval grants no execution policy. Changing the entry, Session, read state, or confirmed usage requires renewed automatic consent. An Agent or receiving-service replacement cancels pending automatic adoption. Read consent retains the observed reading-management sequence, so a later binding change requires renewed confirmation. The panel distinguishes waiting, adoption, connected, ended, superseded, and failed receiving. Cancelling a pending application also cancels reading that has not connected. Stopping sharing after adoption preserves connected reading and its granted automatic permission; pause automatic work or leave reading independently above. The application displays original consent; the reading panel reports current mode and usage. Leave this collaboration ends the remote capture and only the reading created by this join operation. The original local policy returns paused, with lifetime usage retained. The local panel displays that retained policy while the shared-scope panel manages the current combined policy; leaving the local Task first requires leaving the remote scope. Unconfirmed reading cleanup remains visible after capture removal and blocks new applications; the panel reports completion only from confirmed receiving state. The owner lists contribution and read permission separately, including ended contribution with reading still authorized.

The mounted Session entry subscribes to scheduling and activity projections, running state, and connection generation. Activity-only changes refresh status even when scheduling state is unchanged. Projection changes invalidate in-flight status reads; monotonic status watermarks prevent older responses from replacing a later observation. Disconnect and reset clear confirmed state and disable mutations until a fresh status read settles. Each mutation carries the binding shown by the form, remains single-flight until settlement even across reset or panel dismissal, and reconciles by reading status instead of repeating the operation. Receiving-permission drafts survive errors and popover dismissal; changing Session isolates drafts and late callbacks. Outside input composition, Escape closes the open popover and restores trigger focus even after a status change removes the focused control, without activating page shortcuts. Raw Host errors are not rendered.

The panel, forms, Task nodes, graph controls, and minimap follow the shared light or dark palette, including system appearance changes. Connection recovery uses the [shared Connection controller](../connection/README.md#connection-generation); an offline Host cannot be recovered by the collaboration panel’s Refresh action. A successful automatic management read clears its read error. A lost mutation warning remains until an explicit reread or a subsequent action; an explicit reread also acknowledges it when sharing an unfinished automatic read. Unknown-result recovery advice appears after the sent action settles, when Refresh is available; mapped gateway failures follow the same rule.

The collaboration center opens on startup and can be closed from its header or sidebar trigger. Task catalog and focused lineage reads use the Host's configured defaults. Owner observation controls recover whether node identity or the Task catalog returns first after reconnect. While a selected Task is absent during recovery, its detail and actions stay unselected rather than switching to another catalog entry. Refresh and reconnection reload the selected lineage; late replies from earlier selections cannot replace it or overwrite newer Task revisions. Catalog reads preserve Tasks added or updated while they are pending. Assignment and participant replies cannot undo newer binding or presence notifications; a superseded read requests one fresh baseline. A successful presence lease still renews when its returned roster is superseded. Refresh can retry a failed participant announcement; closing the UI stops renewal and waits for sent lease requests before attempting withdrawal. Parent edges are immutable, node drag affects only the current browser view, and Fork or Merge pins each selected parent's exact current revision. The creation preview lets users exclude individual parent publications before the child snapshot is committed. Missing selected Merge parents disable creation until their snapshots return. Publication drafts belong to one Task; a completed publication clears only its submitted draft. Task mutations admit one panel action at a time, and replies from a replaced connection cannot update its catalog. Publications show participant names or, for independent peer reports and terminal notices, a localized source label with the contributor PeerId.

Claude project configuration and session selection remain available without a local Task. For Claude Code, enter a project path on the Host and configure or check its hooks. Open or restart Claude in that project, send a message, and refresh the observed sessions. Select one session. To join a selected Task, enter its responsibility and confirm its allowed directories. A remote Task requires its owner to approve the exact session binding before work observations are shared. The directory starts from the session's working directory and remains editable. Sessions sharing a directory remain independent; the panel never selects or joins them as a group. Failed join or leave requests confirm current Host membership without retrying the mutation. Both actions refresh that Session's mounted source-permission detail so its form reflects the resulting authority.

The ordinary Task-join form collects supported Write/Edit outcomes within the selected directories, including explicitly marked failures, without verifying disk content; they grant no Bash collection or API file reads. Observed, ended, joined, and approved states do not establish liveness or model adoption. The owner panel lists replicated remote bindings and separately displays approved or ended observation intervals; it does not imply that every binding requested Claude capture. Local withdrawal stops collection, while unconfirmed remote withdrawal remains visible with a retry action, including for ended sessions. A pending withdrawal prevents another join or grant update for that session. Removing project hooks retains the shared command profile and existing grants; leave each joined session's Task separately to stop sharing. Configuration conflicts expose a removal action, but the Host refuses to delete edited entries it cannot identify as its own. [Claude scope](../../collaboration/claude-scope/README.md) owns setup and capture limits. A missing Host capability disables these controls with a recovery message.

An independent source pastes one owner-issued application entry and selects an observed session, allowed directories, and expiry, sample, and byte limits. The default source captures that session's Write/Edit activity across the permitted directories without per-file registration; the alternative selects one OpenAPI file and operation. The owner reviews the exact peer, source kind, tools, and limits. Approval enables the source automatically in the Host background, including while its browser page is closed. Tool observations report arguments and success or failure, not verified facts. Local capture, owner contribution, reading, and native automatic starts have separate permissions. [Claude scope](../../collaboration/claude-scope/README.md) owns sampling and background recovery; [scope access](../../collaboration/scope-access/README.md) owns application and grant authority. The secondary manual path transfers a proposal and returned grant explicitly.

The separate “Original Claude session files, commands and reply reports” source offers initially unchecked Write/Edit, exact command and complete Stop reply report categories. At least one category is required; only reply reports can be shared without directories. Commands retain their exact text and ordered directory selection. File permission covers original tool fields, not complete native file content or historical initialization. Stop text may quote user input and does not establish that the turn has ended. Owners approve the complete selection once; permitted future events contribute automatically. Editing categories, commands, directories or limits requires renewed collection consent. Existing captures and route recovery retain their original permission.

A tool-observation or original Claude work joint or reusable group entry offers separate, initially unchecked reading and collection permissions for the selected Claude session. Existing Task or read connections are not replaced. One owner approval connects reading in the Host background without another invitation, including while the source page is closed. The connection prepares context for supported Hooks; it does not start Claude or establish model receipt. Stopping sharing retains adopted reading; leaving the exact collaboration ends its contribution and reading while preserving later independent reads. Its address recovery updates retained routes together, including reading after sharing stops.

Source details recover the original capture after reload or an uncertain operation. Independent Claude read adoption and stopping also refresh the selected Session’s source details, including after a failed reply. Mutations carry its exact identity and remain owned by the Client directory across panel dismissal. Committed Host events invalidate in-flight reads and refresh observed source/application state; reconnect queries a fresh baseline because notifications are not replayed. Failed confirmation retains the last observation and disables mutation controls. Source and owner panels keep the checking status while confirmation is pending; unknown-result recovery guidance appears after that read settles. Other typed errors remain visible during confirmation. Stop preserves cancellation until owner confirmation, including for ended sessions. Updating the same application entry's route preserves its original consent and cancellation state. A reviewed invitation can likewise update only the route of an existing grant; neither recovery path resumes cancelled contribution.

Owner application and contribution inventories are independent of read grants. “Invite multiple sessions to one goal” creates one reusable entry with explicit total applicant slots; rejected, cancelled, and expired applicants retain their slots, and the Host also enforces its global capacity. Each applicant supplies separate consent and receives a separate approval. “Close entry to new applications” blocks new applicants while preserving pending approval until entry expiry and existing member permissions. “End this member’s collaboration” revokes only the selected member’s reading and contribution. Load more advances independent grant, single-entry, group-entry, and per-group application cursors; refresh starts each at its first page. Pagination remains disabled until the authority refresh settles. Group members use distinct application identities; visible public capture IDs and generations match the source panel and distinguish sessions on the same peer. Ending remains available after file contribution ends if reading is still authorized. Single-use entries still accept one capture. Every entry displays its original text for recovery. Clipboard feedback belongs to the displayed transfer document; an old copy result cannot mark a replaced document copied. The UI approves the exact displayed source limits; it does not silently expand them. Grant recovery returns the original permission after a lost reply, while ended grants retain their terminal status. Task changes isolate copied entries and late callbacks. Typed recovery messages omit private diagnostics, and an approved application or active grant does not establish delivery or model adoption.

Committed authorization changes refresh both the member cards and independent reading controls, including changes made by another connected browser. The Client directory owns read inventory, pending mutations and rejection of stale responses across panel dismissal. Reconnect queries fresh authority; failed confirmation retains the last observation with controls disabled and a read-only retry. Receiving or stopping Claude context refreshes its Session independently of inventory confirmation. The [inventory synchronization decision](../../../.agents/notes/implemented/bug-fix/2026-10-24-owner-read-inventory-synchronization.md) explains ownership and notification timing.

MCP client cards distinguish configuration, process presence, per-session Task connection, and context acknowledgement. An incomplete acknowledgement count includes only Sessions that lack the selected revision. The recovery action names `agentharness_task_status` with that Session’s own `bindingId`; listing Tasks or reading a resource does not acknowledge context. The intended MCP session calls `agentharness_task_connect` and retains its own `bindingId`, even when sessions share one client configuration. Setup alone does not join a Task. Setup returns the sent operation’s result; a reply from an earlier connection cannot replace the client directory after reset. A list read started before successful setup cannot replace the resulting configuration or report an obsolete read error.

The header provides the only Task-creation entry. Root creation requires a saved display name, a Task name, and initial shared context. Fork and Merge add immutable parent selection but no plan, stage, acceptance, or review prerequisite. The sidebar badge counts Tasks created by the current identity, displays `0` through `99` or `99+`, and reserves enough width to remain inside the action.

Browser acceptance covers identity confirmation, the single creation entry, Root/Fork/Merge context inheritance, explicit publication, per-session Agent guidance, badge geometry, readable graph-node sizing, and the absence of lifecycle controls.

Native recovery controls update the displayed original capture or read binding. Contribution recovery previews the same application entry with a different owner address; it preserves file permission and pending withdrawal even for a cold Session or expired entry. Joint recovery also carries the displayed read-state comparison. The separate read-route form retains the original subscription, automatic policy, and consumed budget. Host durability and fresh status determine the result; saving a route does not confirm connectivity or model adoption. Without automatic permission, the header and receiving panel retain “Update while I work” after a recorded read issue. Historical read reasons do not establish the latest request’s result or current connectivity. The receiving panel separately shows the current binding’s recorded shared-context bytes, included source count, and size-limit omissions; other nonzero exclusion reasons are expandable. These figures exclude local goal context, chat history, and tool definitions, and establish neither request dispatch, model understanding, nor current remote authorization. Departure or a nonmatching recorded snapshot removes the summary. Step-count changes refresh it during an ongoing turn without polling or starting work.

Capacity omissions also appear on the collapsed collaboration entry for the current ready binding, including when a local Task remains selected. Opening that indication shows the context provider, responsibility and recorded counts. Loading, unavailable, departed and nonmatching records hide it. Zero capacity omissions do not establish complete knowledge. The context provider manages summarization; receiver settings cannot change a remote provider. See the [recorded-capacity decision](../../../.agents/notes/implemented/feature/2026-10-07-scope-recorded-capacity-status.md).

Native local contribution forms and owner-issued single, joint and group entries offer “Completed final answers” as an explicit source choice. Its permission form shows expiry, sample limits and independent answer-disclosure consent; it has no directory, file tool, command or history-initialization fields. Source, limits, Task binding or entry changes require renewed consent. Owners see the exact answer source before approval. Active status and Stop apply to the displayed capture, and an existing capture cannot silently change sources. The [native contribution reference](../../collaboration/scope-agent-contribution/README.md) owns eligibility and disclosure details.

“Files, commands and final answers from one Session” offers an explicit combined selection in local forms and owner entries. A new empty form starts with file tools, exact commands and complete answers unselected, and at least one category is required. Existing file drafts or local file permission can prefill file selections, but still require confirmation. All categories share one sample allowance and stop action. Owner summaries display every selected category, including explicit absence; changing categories clears the final confirmation. Answer disclosure remains explicit because it may include private user inputs. This source excludes historical initialization and is rejected by Claude controls.

<a id="model-experience"></a>

## Model Experience

Indirectly, through operations that delegate model-visible context admission to `dsh-development-task-context`, `dsh-agentharness-bridge`, `dsh-claude-scope`, or `dsh-scope-agent-context`; explicit native automatic permission can start bounded turns while the Agent is idle, whereas passive receiving does not.

#### KV Cache effect

Connecting a session or publishing Task context can change a later request prefix and reduce cache reuse for that session; browser rendering itself adds no model input.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- Node positions are not synchronized across browsers. The UI pins the revisions visible at form submission, and large neighborhoods use bounded placeholders rather than loading an unbounded graph.

- Connection cards show unsupported platforms without setup or manual-configuration actions.

<a id="dev-note"></a>

### Dev Note

Participant, Task, and MCP-client snapshots use the synchronous [Client snapshot store](../store/README.md). The renderer owns each subscription's cleanup, and consumers keep nested snapshot values readonly. Refresh and reset remain directory-owned. Plugin unload invalidates pending Task and MCP inspection or setup replies without starting another read, and the participant directory retains its lease lifecycle; the [state ownership decision](../../../.agents/notes/implemented/simplification/2026-10-25-client-inventory-snapshot-store.md) records notification and development-freezing semantics.

No runtime invariant companion is published because Task and scope authority belongs to Host services; this package owns only browser presentation and interaction state.
